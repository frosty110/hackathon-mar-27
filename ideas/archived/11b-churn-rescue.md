# Idea #11b: Autonomous Customer Churn Rescue Agent

## One-Line Pitch

An autonomous agent that continuously ingests billing, call, and usage data from across your SaaS stack, identifies customers about to churn before humans notice, and proactively calls them with a personalized retention offer.

## The Problem

Every SaaS company bleeds revenue from preventable churn. The warning signs are always there -- declining usage, frustrated support calls, billing downgrades, competitor mentions on sales calls -- but they're trapped in 5 separate tools. Customer success teams manually scrub spreadsheets once a quarter, by which point the customer has already signed a competitor contract. The gap isn't data; it's the absence of an autonomous system that connects signals across sources, reasons about them holistically, and acts before humans even notice the risk.

## The Autonomous Agent Loop

```
[Scheduled Trigger / Continuous Loop]
        |
        v
+-- INGEST (Airbyte) ----------------------------+
|  Stripe: billing events, downgrades, failures  |
|  Gong: call transcripts, sentiment, keywords   |
|  GitHub: API usage decline, integration errors  |
+-------------------------------------------------+
        |
        v
+-- REASON (TrueFoundry LLM Gateway) -----------+
|  Multi-signal churn scoring via LLM reasoning  |
|  NOT threshold rules -- cross-source inference  |
|  "Stripe shows downgrade + Gong call mentioned |
|   competitor + GitHub usage dropped 60%"        |
+-------------------------------------------------+
        |
        v
+-- SEGMENT & STRATEGIZE -------------------------+
|  Tier customers by value x risk                 |
|  Classify churn driver: price / product / rival |
|  Generate per-segment retention playbook        |
+-------------------------------------------------+
        |
        v
+-- STORE (Ghost Postgres + Aerospike) ----------+
|  Ghost: structured analysis runs, audit trail   |
|  Aerospike: vector embeddings of customer       |
|  profiles for similarity search ("who else      |
|  looks like customers we lost last quarter?")   |
+-------------------------------------------------+
        |
        v
+-- ACT (Bland AI) -------------------------------+
|  For highest-value at-risk customers:            |
|  Place a live phone call with personalized       |
|  retention script based on churn signals         |
|  "Hi Sarah, we noticed you haven't used X..."   |
+-------------------------------------------------+
        |
        v
+-- TRACK & LEARN --------------------------------+
|  Record outcomes: saved / lost / pending         |
|  Feed back into future scoring                   |
+-------------------------------------------------+
```

The loop is genuinely autonomous: ingest, reason, act, learn. No human in the loop between data pull and phone call. That is what makes it an agent and not a dashboard.

## Sponsor Stack (3+ required)

### 1. Airbyte -- Multi-Source Data Ingestion (ESSENTIAL)

**What it does:** Pulls structured data from Stripe (billing history, plan changes, failed payments, MRR), Gong (call transcripts, sentiment scores, competitor mentions), and GitHub (API call volume, error rates, integration activity).

**Why it's load-bearing:** This is the foundation the entire agent stands on. Without multi-source ingestion, there is no multi-signal reasoning -- you'd just have a billing alert system. All three of Airbyte's available agent connectors (Stripe, Gong, GitHub) map directly to distinct churn signal categories. Remove Airbyte and the agent collapses to a single-source toy.

**Verdict: ESSENTIAL.** This may be the single strongest Airbyte use case across all hackathon ideas. Three connectors, all naturally justified, none forced.

### 2. Bland AI -- Autonomous Phone Outreach (ESSENTIAL)

**What it does:** Places live voice calls to at-risk customers with a personalized retention script generated by the agent. Handles the conversation, responds to objections, offers retention incentives.

**Why it's load-bearing:** The call is the action. Without it, the agent is just an analytics dashboard that produces reports nobody reads. The phone call is what makes this an autonomous agent rather than a BI tool. It's also the unforgettable demo moment.

**Verdict: ESSENTIAL.** The entire "rescue" in "Churn Rescue Agent" depends on this.

### 3. TrueFoundry -- Multi-LLM Gateway (ESSENTIAL)

**What it does:** Routes LLM calls for churn reasoning, sentiment analysis, strategy generation, and call script writing. Potentially uses different models for different tasks (fast model for sentiment extraction, reasoning model for churn scoring, creative model for call scripts).

**Why it's load-bearing:** The agent needs LLM reasoning at multiple stages: parsing Gong transcripts, scoring churn risk across signals, generating retention strategies, writing personalized call scripts. TrueFoundry provides the unified gateway for all of this plus model routing.

**Verdict: ESSENTIAL.** Core reasoning engine for the agent.

### 4. Ghost -- Agent-Managed Postgres (ESSENTIAL)

**What it does:** Stores per-run analysis results, customer risk scores over time, intervention history, and outcome tracking. The agent creates and queries its own database via MCP.

**Why it's load-bearing:** The agent needs persistent state to track risk trajectories over time ("this customer's score went from 0.3 to 0.7 over 3 weeks") and record which interventions worked. Without storage, every run is stateless and the feedback loop breaks.

**Verdict: ESSENTIAL.** Required for the "Track & Learn" phase and longitudinal analysis.

### 5. Aerospike -- Vector Search for Customer Similarity (USEFUL)

**What it does:** Stores vector embeddings of customer profiles and churn patterns. Enables similarity search: "show me active customers who look like customers we lost last quarter."

**Why it's load-bearing:** Adds a genuinely useful capability (pattern matching across customer base) but the core loop could function without it. It elevates the agent from reactive to predictive.

**Verdict: USEFUL but not strictly essential.** Strong value-add, but could be cut if build time runs short.

### 6. Auth0/Okta -- API Authentication (SUPPORTING)

**What it does:** Manages OAuth tokens for Stripe, Gong, and GitHub API access. Token vault stores and refreshes credentials.

**Why it's load-bearing:** The agent needs authenticated access to 3+ external APIs. Auth0 handles token lifecycle so the agent doesn't store raw credentials.

**Verdict: SUPPORTING.** Necessary infrastructure but not differentiated. Judges won't remember it, but it's good practice.

### 7. Overmind -- LLM Observability (COSMETIC)

**What it does:** Tracks LLM call costs, latency, and quality across the agent's reasoning pipeline.

**Why it's load-bearing:** It isn't, really. Nice for a "here's what this run cost" slide but doesn't change agent behavior.

**Verdict: COSMETIC.** Add if time permits. Drop-in SDK makes it low-effort.

**Tool count: 5 essential/useful + 2 supporting/cosmetic = 7 sponsor tools. Comfortably exceeds the 3-tool minimum with at least 4 that are genuinely load-bearing.**

The judge's phone rings.

The agent has just analyzed data from Stripe, Gong, and GitHub. It identified "Sarah Chen" as a high-value account at severe churn risk: she downgraded her Stripe plan last month, her last Gong call transcript included "we've been evaluating [competitor]," and her team's GitHub API usage dropped 60% in two weeks.

The agent generated a personalized retention strategy and placed a call via Bland AI. A phone sitting on the demo table rings. The voice on the other end says:

> "Hi Sarah, this is Alex from Acme. I wanted to personally reach out because I noticed your team hasn't been using our API integration features recently, and I want to make sure everything is working well for you. We actually just shipped some improvements to the integration layer that I think would address the reliability issues your team flagged. I'd also love to offer you a complimentary upgrade to our Pro tier for the next quarter so you can evaluate the full platform. Would you have 15 minutes this week to walk through what's changed?"

That's the demo. Data in, reasoning in the middle, phone call out. The entire loop, live, in under 3 minutes.

**Key implementation notes:**
- Orchestrator is a Python script using Airbyte PyAirbyte for connectors
- LLM calls go through TrueFoundry gateway (model selection per task)
- Ghost MCP for database creation and queries (no manual DB setup)
- Bland AI REST API for call placement (simple POST with script + phone number)
- Auth0 for secure token storage/refresh across Stripe, Gong, GitHub APIs
- Entire pipeline can run in ~60 seconds for a demo-sized dataset

## Buildability Risk Assessment

| Component | Difficulty | Risk | Mitigation |
|-----------|-----------|------|------------|
| Airbyte Stripe connector | Low | Docs are solid, PyAirbyte works | Use sample/test Stripe data |
| Airbyte Gong connector | Medium | Need Gong test account with data | Pre-load synthetic transcripts or use Gong sandbox |
| Airbyte GitHub connector | Low | GitHub API is well-documented | Use a real repo with synthetic usage patterns |
| LLM churn reasoning | Low | Prompt engineering, not model training | Test prompts early, iterate |
| Bland AI call | Low | Simple REST API, well-documented | Test early, have a backup phone number ready |
| Ghost Postgres | Low | MCP interface, standard SQL | Schema is simple (customers, scores, interventions) |
| Aerospike vectors | Medium | Learning curve for vector indexing | CUT FIRST if behind schedule |
| Auth0 integration | Medium | OAuth flow setup takes time | Can hardcode tokens for demo if desperate |
| End-to-end orchestration | Medium | Gluing 5+ services together | Build linearly: Airbyte first, then LLM, then Bland |
| Demo data realism | Medium | Fake data looks fake | Invest 1 hour in crafting realistic sample data |

**Overall build risk: MODERATE.** The individual components are straightforward. The risk is integration time -- 7 services is a lot of glue code in 8 hours. The critical path is: Airbyte connectors working -> LLM reasoning producing good output -> Bland AI making a call. Everything else is additive.

**Recommended build order:**
1. Hours 1-2: Airbyte connectors pulling real/sample data from all 3 sources
2. Hours 2-4: LLM reasoning pipeline (churn scoring, strategy generation)
3. Hours 4-5: Ghost Postgres storage, outcome tracking
4. Hours 5-6: Bland AI call integration with generated scripts
5. Hours 6-7: End-to-end integration, Auth0, Aerospike if time permits
6. Hours 7-8: Demo prep, data polish, rehearsal

## Honest Weaknesses

1. **Synthetic data risk.** Unless you have a real Stripe account with real billing history, a real Gong account with real call recordings, and a real GitHub org with real usage data, you're demoing with fake data. Judges may discount the Airbyte integration if it's clearly pulling from a seed dataset you created 2 hours ago. Mitigation: make the data realistic and be transparent -- "we seeded representative data to demonstrate the pipeline."

2. **Gong access is the hardest connector.** Gong API access requires an enterprise account and API credentials. If you can't get a Gong sandbox, you may need to mock the Gong data and only run Stripe + GitHub connectors live. This weakens the "3 connectors" story.

3. **The call is a parlor trick (slightly).** Bland AI is impressive, but the voice call in the demo is somewhat theatrical. In production, you'd probably want human approval before an AI calls a customer. Judges who think about this will note that full autonomy here is a liability, not a feature. Mitigation: frame it as "agent drafts the call and places it; in production, you'd add an approval gate for calls above $X ARR."

4. **Churn scoring is hard to validate in a demo.** You can show the agent saying "risk score: 0.91" but the judges can't verify that's correct. The reasoning chain helps, but it's still "trust the LLM." Mitigation: show the reasoning chain explicitly, not just the score.

5. **7 tools is ambitious.** Every additional integration is another failure point during a live demo. The Auth0 and Overmind integrations might not be worth the demo risk. Mitigation: get the core 4 (Airbyte, TrueFoundry, Bland, Ghost) rock-solid first. Add extras only if stable.

6. **Not novel in concept.** Churn prediction is a well-known problem. The novelty is in the autonomous action loop, not the idea itself. Judges who've seen churn dashboards before might underweight the innovation. Mitigation: emphasize the autonomy -- "this isn't a dashboard, it makes the call."

**Autonomy (5/5):** This is a textbook autonomous agent loop -- ingest, reason, act, learn. No human in the loop. Multi-source data fusion with LLM reasoning, not threshold rules. The agent takes real-world action (phone call) based on its own analysis. This is what the hackathon is looking for.

**Idea (4/5):** Universal problem, every judge gets it instantly, clear business value. Loses a point because churn prediction itself isn't novel -- the innovation is in the autonomous action, not the detection. Still, "the agent calls the customer" is a compelling differentiator.

**Technical Implementation (4/5):** Multi-source data ingestion, LLM reasoning chains, vector similarity, persistent storage, voice API integration. Solid technical depth. Not quite a 5 because the individual components are well-trodden (API calls + LLM prompting + REST call), just well-composed.
